## 5. Kurzfazit

Das vierte Maßnahmenprogramm hat die Runde-4-Befunde beider Dimensionen weitgehend geschlossen: Das Rechenbudget erfasst jetzt Hedge-Instrumente (400 statt 422), bindet die Store-bewertenden GET/POST-Routen an das Request-Budget und begrenzt den Store kumulativ mit Netting; `TRUST_PROXY` macht das Rate-Limit hinter einem Gateway tatsächlich zu einem Client-Limit (CIDR-Liste verifiziert), Health-Probes sind ausgenommen; ungültige Kalenderdaten sind Eingabefehler mit eigenem Code im Core und 400 an der API; jede Inline-Fehlerantwort trägt einen der 34 katalogisierten Codes; EMIR-Meldedaten reisen per POST-Body, die Logs enthalten keine Query mehr, und die ITS-Wertebereiche (`Y/N/I`, `TRUE/FLSE/UKWN`, `TRUE/FLSE`) werden vom Core erzeugt und vom Vertrag typsicher fixiert. Der OpenAPI-Vertrag (41 Operationen, 16 Komponenten, 0 unaufgelöste Referenzen, 0 singuläre `example`, `text/csv` deklariert) ist formal sauber, Tests (321/85/242), Lint, Prettier, Typecheck und – diesmal ausführbar – `pnpm audit` sind grün. Dokumentation und Regulatorik-Mapping sind konsistent mit dem Code (Operationen, Trades, Codes, Env-Namen, Feldnummern gegen externe Quelle bestätigt) und ehrlich in dem, was offen bleibt. Neu und gewichtigstes Thema ist eine Konsistenzlücke im Fehlerobjekt: Schema-Verstöße und JSON-Parse-Fehler – die häufigsten Client-Fehler – tragen keinen `code`, während README und SECURITY „jede Fehlerantwort“ zusichern. Der Rest sind kleine Architektur- und Hygienepunkte (unbekannte Routen ohne Rate-Limit, schwache ETags in `If-Match`, Frequenz-Pattern der Hedge-Amortisation, ein monolithischer Commit ohne Typ) sowie die zwei bewusst offenen Posten: das in ADR-026 geplante, aber nicht umgesetzte Bundle-/Coverage-Budget und der fehlende Release-Tag.
