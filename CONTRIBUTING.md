# Mitwirken an DERIVA

## Entwicklungsumgebung

```bash
pnpm install
pnpm build          # Core → API → Web in dieser Reihenfolge (API/Web importieren das Core-dist)
pnpm test           # baut vorher den Core (pretest) und führt alle Tests aus (Core, API, Web)
pnpm dev            # Core im tsc-Watch + API auf :4000 + Web auf :5173 (parallel, gestreamt)
pnpm typecheck && pnpm lint && pnpm format:check
```

**Node ≥ 22.22** (LTS; `.nvmrc`/`.node-version` = `22`, `package.json#engines`, `engine-strict=true` in `.npmrc` – `pnpm install` bricht auf einem älteren Node mit der `engines`-Meldung ab; die CI-Matrix läuft auf 22 und 24), pnpm 10 (Version aus `package.json#packageManager`). Node 20 ist seit April 2026 EOL und kann die Web-Tests nicht ausführen (jsdom 30 / vitest 5 / undici 8, siehe ADR-020, Review R7 N7-01). Einzelne Pakete: `pnpm dev:core`, `pnpm dev:api`, `pnpm dev:web`, `pnpm --filter @deriva/api test`.

**Warum `pnpm build` vor allem anderen?** `apps/api` und `apps/web` importieren `@deriva/pricing-core` aus `packages/pricing-core/dist` (`exports` zeigt auf `dist`). Ein veraltetes `dist` liefert alte Ergebnisse, ohne dass ein Test fehlschlägt – deshalb bauen `pnpm test`/`pnpm typecheck` den Core vorher (`pretest`/`pretypecheck`), die CI baut ihn explizit, und `pnpm dev` hält ihn per `tsc --watch` aktuell. Vor einer Abgabe immer `pnpm build` ausführen, damit `apps/api/dist` und `apps/web/dist` dem Quellstand entsprechen (`node apps/api/dist/server.js` meldet die Version unter `GET /api/health`).

## Struktur und Regeln

- **Pricing-Core** ist nebenwirkungsfrei: keine I/O, keine Node-APIs, keine Mutation von `MarketContext`/`Curve`. Domänenfehler werfen `PricingError` mit `code` (ADR-022). Neue Instrumente = Typ in `instruments/types.ts` + Pricer in `pricing/` + Case im Dispatcher `pricing/price.ts` + Builder + Editor-Case (`apps/web/src/components/TradeEditor.tsx`) + Badge (`lib/trade-ops.ts`) + JSON-Schema-Variante (`apps/api/src/schemas.ts`, `oneOf` je `type`) + Datums-Schlüssel (`apps/api/src/lib/dates.ts`).
- **Datumsangaben** intern als Serial-Dates, an der API als ISO-8601 (`apps/api/src/lib/dates.ts`).
- **API-Vertrag:** jede Route hat `operationId`, `schema.body`/`querystring`/`params` und `response` (2xx + Fehler über `responses(...)` in `schemas.ts`; Health-Routen über `responsesUnlimited(...)`, weil sie vom Rate-Limit ausgenommen sind); der Vertragstest `apps/api/src/contract.test.ts` friert die Operationsliste ein (44 Operationen) und prüft, dass jeder Sample-Trade der Builder das Schema passiert; `review-r3.test.ts` prüft OpenAPI 3.1, benannte Komponenten, `discriminator.mapping` und die Auflösung aller `$ref`; `review-r4.test.ts` prüft Budget-Abdeckung, Fehlercodes, ITS-Formate und die Core-Import-Allowlist; `review-r5.test.ts` erzwingt auf jeder Operation mit Request-Body einen Schema-Verstoß und prüft den Katalog-Code (`VALIDATION_ERROR`), Parse-/Medientyp-Fehler (`INVALID_JSON`, 415 auch für `text/plain`), das Rate-Limit unbekannter Routen, starke ETags nach RFC 9110, das Hedged-Item-Budget, die Vol-Flächen-Strukturprüfung (`VOL_SURFACE_INVALID`) und die Betragsobergrenze `MAX_AMOUNT`; `review-r6.test.ts` prüft die elf CSV-Vorlagen im Round-Trip (Vorlage → Import → Bewertung), `collateralCurrency: none`, die Zeilen-Schemaprüfung (`CSV_ROW_INVALID` statt 400), Medientypen (`text/plain`/`text/csv` → 415), „415 nur auf Operationen mit Body“ und dass kein Fehlerobjekt an `sendError` vorbei entsteht; `review-r7.test.ts` prüft die Node-Anforderung an ihren vier Stellen, den starken `StoredTrade.etag` (Pattern), die Diskontzuordnung von `POST /api/market/curves`/`PUT /api/market`, die Beispiel-Fixings beim Stichtagswechsel, die CCS-Spaltenaliase, die Register-Endpunkte samt Snapshot-Envelope (ADR-027), `?dryRun=1` und die Ablehnung unbekannter Query-Parameter sowie `UNKNOWN_INDEX`; `review-r8.test.ts` prüft den Stichtagswechsel mit Laufzeitkurve, Zuordnungen und Vol-Override (N8-01, Sample- und Import-Modus, `MARKET_STATE_DROPPED:`), die Währungsprüfung der Collateral-Zuordnung (N8-02), den Export-ETag mit Register-Anteil (N8-03), den atomaren Envelope-Import (N8-04), das Kalender-Register (R8-2), Par-Risiko für Laufzeitkurven und `PAR_RISK_INCOMPLETE:` (R8-3), den Import aller elf Workstation-Vorlagen – die eingecheckte Runde-8-Kopie und, wenn auswertbar, die lebenden Vorlagen aus `apps/web/src/lib/portfolio-io.ts` – samt Spread-Einheitsregel (R8-4) sowie die Vollständigkeit der Präfixlisten in README/Architektur und die Toolchain-Dateien (commitlint, typbewusstes Lint); `review-r10.test.ts` prüft die drei Reviewer-Szenarien der Runde 10 (Markt R10-1: `POST /api/market/curves EUR-ESTR` baut die Abhängigen neu und liefert Par ≈ DV01 im Ursprungsprozess; Export → frische API → Par ≈ DV01 statt −97 521, Roll und `discardImport`; Fremd-EoD ohne `quotes` → `curvesWithoutQuotes[]`, mit fremden `quotes` → `curvesInconsistent[]`/`PAR_RISK_INCONSISTENT:`), die Index-Währung in `quotesProblems`, N10-02 (Sample-Id im `quotes`-Block wird bei `discardImport` benannt verworfen), den ordnungsunabhängigen Register-Hash/ETag, die Abhängigkeitshelfer in `lib/curve-specs.ts`, die Timeouts (N10-03) und die Dokumentwortlaute der Runde 10 (N10-04, N10-01, 13 Präfixe, 0.3.1); `review-r9.test.ts` prüft die Envelope-Vorprüfung mit zusammengesetzten Kalender-Ids (N9-01, Regel `substitutePendingCalendar`), den Import-Roll ohne `meta.snapshotTime` mit markiertem Label und EMIR-Feld 23 = neuer Stichtag (N9-02), die Diskontkurven-Regel im Rebuild (N9-03, DKK-Szenario und `isDiscountCurve: false`), den Envelope-Block `quotes` (R9-1: Export, Import in frische Instanz, Par-Buckets, ETag, 422 bei ungültigen Einträgen, Komponente `CurveBuildSpec`), die `type`-Spalte der CSV-Vorlagen (R9-4: Token der Workstation, Abgleich mit `?type=`, Ablehnung je Zeile) und die drei nachgezogenen Sätze (N9-04); `envelope-fresh-process.test.ts` ist absichtlich eine **eigene Datei**: Vitest gibt ihr einen frischen Worker mit leerem Core-Register, und der Import läuft zusätzlich in einem Kindprozess (`node --import tsx`) – so wird belegt, dass ein exportierter Envelope mit `CZ-X9+TARGET` in einem Prozess importiert, der den Kalender nie gesehen hat. Body-lose Operationen (`GET`, `DELETE`) bauen ihre Antwortkarte mit `responsesWithoutBody(...)` (kein 415), Operationen mit Body mit `responses(...)`. Geteilte Schemas tragen ein `$id` (wird zum Komponentennamen) und werden in `app.ts` per `addSchema` registriert; neue Trade-Varianten kommen in `tradeVariantSchemas`. Fehler laufen ausschließlich über `lib/errors.ts` (ADR-025): Inline-Fehler (404/409/412/428/400) über `sendError(reply, req, status, code, message, extra?)` mit einem Code aus `API_ERROR_CODES.api` – ein neuer Code wird dort eingetragen und in der `ErrorResponse.code`-Beschreibung erklärt (der Vertragstest prüft beides); Codes, die als String ankommen (Core-Codes), gehen durch `apiErrorCode(code, fallback)`. Bewertungsbezogene Routen setzen `config: { marketHeader: true }` (Header `X-Market-Snapshot-Id`); Routen, die viele Bewertungen je Trade auslösen, deklarieren `computeWeight`, Routen, die den Trade-Store bewerten, `storeFallback` (`true` oder ein Prädikat auf dem Request, z. B. `?price=1`), Routen, die Trades speichern, `storeWrite` (Store-Budget `MAX_STORE_PERIODS`) – alles `lib/limits.ts`.
- **Core-Importe der API:** `apps/api` importiert nur die in ADR-024 als öffentlich benannte Oberfläche von `@deriva/pricing-core`; `review-r4.test.ts` („N3-04“) grept alle Importe gegen die Allowlist. Braucht eine Route eine weitere Core-Funktion, wird sie erst in ADR-024 als öffentlich aufgenommen (und in der kuratierten `index.ts` exportiert – interne Helfer liegen seit Runde 6 hinter `@deriva/pricing-core/internal` und sind für die Apps tabu), dann in der Allowlist des Tests.
- **CSV-Import:** Spaltenvorlagen je Produkt liegen in `apps/api/src/lib/csv-import.ts` (`CSV_TEMPLATES`, `csvTemplateText`; elf Vorlagen – `BasisSwap`/`AmortisingSwap`/`ImmSwap` bauen `InterestRateSwap`s, siehe `CsvTemplate.tradeType`); die OpenAPI-Beschreibung von `POST /api/trades/import` wird daraus generiert. Jeder gebaute Trade wird in der `preValidation` gegen das `Trade`-Schema geprüft (Verstoß → `rejected`/`CSV_ROW_INVALID` je Zeile). Eine neue Spalte = Template + `buildTrade`-Mapping (+ deutscher Alias in `ALIASES`) + Round-Trip-Test in `review-r3.test.ts`/`review-r6.test.ts`; jede Vorlagendatei beginnt seit Runde 9 mit der Spalte `type` und dem Typ-Token der Workstation (`CSV_TYPE_TOKENS`: `IRS`, `FXF`, `CAP`, `SWPT`, `FXO`, `CCS`, `FRA`, `FXS`, `BASIS`, `AMORT`, `IMM` – identisch mit `CSV_TRADE_TYPES` der Web-Datei, der Test `review-r9.test.ts` vergleicht beide), der Reader gleicht die Spalte mit `?type=` ab (`csvTypeMismatch`, Zeile abgelehnt bei Widerspruch); ein neuer Typ braucht also auch ein Token auf beiden Seiten; Spaltennamen mit der Web-Vorlage (`apps/web/src/lib/portfolio-io.ts`) abstimmen – die API-Namen sind die Referenz, die Web-Vorlagen schreiben sie, ältere Web-Namen bleiben Aliase (`canonicalColumn`, Markt R7-5). Query-Parameter der Import-Route sind mit `additionalProperties: false` deklariert (ein vertippter Parameter ist ein 400, kein stiller Import); `?dryRun=1` teilt den Handler-Pfad bis zum `upsert`.
- **Tests sind Pflicht**: Referenzwerte (Haug/Hull/QuantLib), Paritäten, Round-Trips. `vitest run` muss in allen Paketen grün sein; Coverage-Schwellen in den `vitest.config.ts`. **Timeouts (Runde 10, N10-03):** `apps/api/vitest.config.ts` setzt `testTimeout` **und** `hookTimeout` auf 30 s – `buildApp()` bootstrappt den Sample-Markt (≈ 2 s kalt), mehrere Integrationstests bauen zwei oder drei Instanzen und jede Datei eine im `beforeAll`; unter CI-Last (API- und Web-Suite parallel auf einem 2-Core-Runner) überschritten beide den Vitest-Default von 10 s, ohne dass ein Test fehlgeschlagen wäre (30 übersprungene Tests, Exit 1). Die Reserve ist bewusst großzügig, ein echter Hänger fällt weiterhin auf; die Web-Konfiguration (`apps/web/vite.config.ts`, 20 s) pflegt der Web-Owner. Ein Test, der länger als 10 s _braucht_, bekommt zusätzlich einen eigenen Timeout im `it(…, ms)` mit Begründung (Beispiel `envelope-fresh-process.test.ts`).
- **Formatierung:** Prettier (`.prettierrc.json`, `.editorconfig`); `pnpm format` vor dem Commit, `pnpm format:check` ist CI-Gate. Prosa-Dokumentation unter `docs/` ist bewusst ausgenommen (`.prettierignore`).
- **Lint:** ESLint flat config (`eslint.config.js`, `--max-warnings 0`); `eslint-plugin-react-hooks` ist aktiv (`react-hooks/rules-of-hooks` als error, `react-hooks/exhaustive-deps` als warn – beides blockiert wegen `--max-warnings 0`) für `apps/web/src/**`. **Typbewusstes Lint (Runde 8, N4-03):** `tseslint.configs.recommendedTypeChecked` gilt für `packages/pricing-core/src/**` und `apps/api/src/**` (`parserOptions.projectService` gegen die jeweiligen `tsconfig.json`) – `no-floating-promises`, `no-misused-promises`, `await-thenable`, `only-throw-error` und die `no-unsafe-*`-Familie sind aktiv; `restrict-template-expressions` erlaubt Zahlen/Booleans (Kennzahlen und Ids in Fehltexten), `no-base-to-string` und `require-await` sind aus (bewusste `String(x)`-Zitate, Fastify-`async`-Handler ohne `await`). Für den Core sind drei Regeln mit Altbefunden geparkt (`no-unnecessary-type-assertion` 13 + 17 in Tests, `no-redundant-type-constituents` 19, nullable Template-Ausdrücke 14) – sie werden mit der nächsten Core-Runde eingeschaltet; Tests dürfen `.json() as …` casten (`no-unnecessary-type-assertion` aus) und `any` in Templates nutzen. Seit Runde 9 gilt `recommendedTypeChecked` auch für `apps/web/src/**`: `restrict-template-expressions` mit `allowNullish` (Kennzahlen, Ids und optionale Werte in UI-Texten); nur in Web-**Tests** sind `no-unnecessary-type-assertion` und `unbound-method` (Testing-Library-Getter) aus – in den Web-Quellen ist der gesamte typbewusste Satz aktiv (Promise-Stellen in Effekten bereinigt).
- **Sprache:** Code, Typen, Kommentare Englisch; UI, Reports, Dokumentation Deutsch.
- **Hotkeys** werden ausschließlich in `apps/web/src/hotkeys/keymap.ts` deklariert (Single Source of Truth für Dispatcher, Palette, Cheat-Sheet, Doku).
- **Architekturentscheidungen** als ADR in `docs/architecture/02-adrs.md` dokumentieren; regulatorisch relevante Features zusätzlich im Mapping `docs/compliance/01-regulatorik-mapping.md` (Anforderung → Feature → Evidenz → Status) nachziehen.

## Commits und Pull Requests

- Conventional Commits (`feat:`, `fix:`, `docs:`, `test:`, `refactor:`, `chore:`), Betreff ≤ 72 Zeichen, Body erklärt das Warum. **Commit-Lint (Runde 8, N6-03a):** `commitlint.config.mjs` (`@commitlint/config-conventional`, `header-max-length` 72, `scope-enum` `core`/`api`/`web`/`ci`/`docs`/`quality`/`repo`/`deps`/`release`/`product`/`compliance`/`research` – mehrere Scopes mit Komma, `feat(core,api): …`; `subject-case` ist aus, weil deutsche Betreffzeilen Substantive großschreiben; Body-Zeilen sind unbegrenzt). Es gibt **keinen** lokalen Git-Hook: der CI-Job `commitlint` prüft bei Pull Requests die Range `base…head` und bei Pushes die Range `before…sha` (bei Branch-Erstellung/Force-Push nur `HEAD`) – die Betreffzeilen der Runden 4–7 in der Historie bleiben unangetastet. Lokal: `pnpm lint:commits` (Default `HEAD~1..HEAD`, `COMMITLINT_FROM=<sha> pnpm lint:commits` für eine größere Range) oder `printf 'feat(api): …\n' | npx commitlint`. **Pflicht seit Runde 10 (N10-01):** `pnpm lint:commits` ist **vor jedem Commit** auszuführen – konkret die geplante Betreffzeile mit `printf '<betreff>\n' | npx commitlint` prüfen und unmittelbar nach dem Commit, vor dem Push, `pnpm lint:commits` (bzw. `COMMITLINT_FROM=<basis> pnpm lint:commits` für die ganze Programm-Range) laufen lassen; ein roter Lauf wird sofort mit `git commit --amend` korrigiert, solange der Commit noch nicht gepusht ist. Anlass: der Release-Commit der Runde 9 (`8fbf579`, Betreff 74 Zeichen) brach das eigene CI-Gate auf der Programm-Range; die Historie wird nicht umgeschrieben, die Regel gilt für jeden weiteren Commit. Programme mit neuen öffentlichen Namen (Core-Exporte, Vertragsfelder) heißen `feat(...)`, nicht `fix(...)`.
- **Präfix mit Scope und kleine, zusammenhängende Commits** (Review R5, N5-05): Betreff als `type(scope): summary` mit dem Paket bzw. Bereich als Scope (`feat(core): …`, `fix(api): …`, `feat(web): …`, `docs(compliance): …`, `chore(ci): …`, `test(api): …`); ein Commit je Änderungsprogramm oder Befund – Core-Bewertung, API-Vertrag, Web und Dokumentation kommen als getrennte Commits (bzw. PRs), damit jeder Commit für sich reviewbar und bisect-fähig bleibt. **Maßnahmenprogramme einer Review-Runde werden je Programm committet** – `feat(core): …`/`fix(core): …` für den Pricing-Core, `feat(api): …` für API und Vertrag, `feat(web): …` für die Workstation, `chore(ci): …`/`docs: …` für Toolchain und Dokumentation (Review-Berichte als `docs(quality): …`) – nicht als ein Sammel-Commit über alle Pakete: die Runden 4–6 landeten mit 85, 108 und 97 Dateien in je einem Commit (Review R5 N5-05, R6/R7 N6-03a); ab Runde 7 gilt die Aufteilung je Programm, ab Runde 8 erzwingt der CI-Job `commitlint` Form und Betrefflänge für neue Commits (siehe oben). `feat` für neue Funktionen (auch in einem Fix-Programm), `fix` nur für Korrekturen; Review-Berichte und Scorecards als eigener `docs(quality): …`-Commit, Produkt-Doku als `docs(product): …`.
- Jede PR folgt `.github/pull_request_template.md`: Beschreibung, betroffene Epics/User Stories (`docs/product/02-epics-und-user-stories.md`), CHANGELOG-Eintrag, grüne CI (Typecheck, Lint, Prettier, Tests mit Coverage, `pnpm audit`, Builds, E2E). Reviews werden über `CODEOWNERS` angefordert.
- Abhängigkeits-Updates kommen über Dependabot (`.github/dependabot.yml`): Gruppen `fastify`, `react`, `tooling` (Minor/Patch) und `tooling-major` (Major-Releases der Toolchain als eigener wöchentlicher PR). Manuelle Upgrades bitte mit `pnpm audit --prod --audit-level=high` prüfen. **Toolchain-Stand (Runde 6, N4-04):** vitest 5.0 / `@vitest/coverage-v8` 5.0 (Core, API, Web), vite 8.2 (Rolldown-Bundler; `manualChunks` in `apps/web/vite.config.ts` wird weiter honoriert, der Build emittiert zusätzlich einen `rolldown-runtime`-Chunk – das Größenbudget `scripts/size-limit.mjs` bleibt grün), `@vitejs/plugin-react` 6.1, jsdom 30.0. Der Sprung war **nicht** konfigurationsneutral (Review R7, N7-04): vitest 5 zählt Statements getrennt von Lines, deshalb wurden die Web-Coverage-Schwellen in `apps/web/vite.config.ts` von Lines 80 / Branches 70 / Statements 80 auf **Lines 78 / Statements 75 / Branches 68 / Functions 50** angepasst und `testTimeout: 10000` gesetzt (Lazy-Views unter Testlast); der Core erhielt `coverage.exclude` für `src/internal.ts` und `tsconfig.json` den Typ `node`; in Runde 7 kam `testTimeout: 20000` im Core hinzu (N7-03). **Node-Anforderung (Runde 7, N7-01):** jsdom 30 verlangt Node `^22.22.2 || ^24.15.0`, vitest 5 `^22.12 || ^24` – Node 20 (EOL April 2026) startet den Vitest-Worker der Web-Tests nicht mehr (`undici@8`: `webidl.util.markAsUncloneable is not a function`; reproduzierbar mit `PATH=/opt/node20/bin:$PATH npx vitest run src/lib/lazy.test.tsx` in `apps/web`). Deshalb `engines.node >=22.22`, `.nvmrc`/`.node-version` = `22`, `engine-strict=true`, CI-Matrix **22/24** (Node 20 entfernt). **Offen:** echarts 6 vor dem 2026-12-31 (Ablauf der Advisory-Ausnahme in `SECURITY.md`; der Wechsel berührt den Chart-Wrapper `EChartImpl.tsx` und die Theme-Tokens und wird mit den E2E-Diagramm-Checks als eigener PR eingespielt). **TypeScript bleibt auf 5.x gepinnt** (`ignore` in `dependabot.yml`): `typescript-eslint` deklariert seinen unterstützten TS-Bereich je Release, und die Modul-Einstellungen `NodeNext` (API) / `Bundler` (Core, Web) sind gegen 5.x geprüft; ein TS-Major wird bewusst zusammen mit einem `typescript-eslint`-Release eingespielt, das ihn unterstützt.
- Keine Marktdaten mit Lizenzbeschränkung committen; der Beispielmarkt ist indikativ.

## Generierte Dateien und Referenzdaten

- **`packages/pricing-core/src/version.ts`** (Quelle von `ENGINE_VERSION`) wird aus `package.json#version` erzeugt: `pnpm --filter @deriva/pricing-core run version:gen` (läuft automatisch als `prebuild`/`pretest`). Nach einer Versionsänderung die regenerierte Datei **committen** – die CI führt `version:gen` aus und bricht mit `git diff --exit-code` ab, wenn sie von der eingecheckten abweicht.
- **Golden Master** (`packages/pricing-core/test-data/golden/*.json`, ADR-021): `python3 packages/pricing-core/tools/quantlib-golden.py` erzeugt die Referenzwerte aus geschlossenen Formeln und ergänzt bei installiertem QuantLib einen Cross-Check-Block; `src/testing/golden.test.ts` prüft sie mit 1e-6 relativer Toleranz. Nur regenerieren, wenn eine Konventions- oder Modelländerung die Referenz selbst betrifft – mit Begründung im CHANGELOG („Geändert“) und Verweis auf die Herleitung in `test-data/golden/README.md`.

## Release

- Version in allen `package.json` (Root, Core, API, Web) anheben, `version:gen` ausführen, CHANGELOG-Abschnitt mit Datum abschließen, Vergleichs-Links ergänzen.
- `pnpm build && pnpm test`, danach den freigegebenen Commit taggen: `git tag -a v0.2.0 -m "DERIVA 0.2.0"` und `git push --tags`.
- **Wann getaggt wird (N4-10):** Tags werden **am Ende einer Qualitätsrunde** auf den letzten Commit des Maßnahmenprogramms gesetzt – nach dem Programm-Commit (`feat(api,ci,docs): …` als letzter der drei Programm-Commits) und vor dem nächsten Review –, nie auf Zwischenstände innerhalb einer Runde. Für 0.2.0 heißt das: `v0.1.0` rückwirkend auf `2cb1571` (der erste Commit, der 0.1.0 auslieferte), `v0.2.0` auf den HEAD nach Runde 8; die Vergleichs-Links im CHANGELOG (`compare/v0.1.0...v0.2.0`, `releases/tag/v0.1.0`) sind auf genau diese beiden Tags ausgelegt. Tags werden lokal annotiert gesetzt und von einem Maintainer mit Tag-Push-Recht veröffentlicht (`git push origin v0.1.0 v0.2.0`); aus einer Umgebung, deren Push-Berechtigung auf den Arbeitsbranch beschränkt ist, schlägt der Tag-Push mit HTTP 403 fehl. Stand: `v0.1.0`, `v0.2.0` und `v0.3.0` (→ `e68cb34`) sind lokal gesetzt, Veröffentlichung durch Maintainer ausstehend. Runde 10 hat die Version auf **0.3.1** gehoben (Patch: Härtung ohne neue Funktionsoberfläche, CHANGELOG `[0.3.1]`); der Tag `v0.3.1` folgt dem Programm-Commit der Runde 10 nach derselben Regel. Die nächste Runde erhöht die Version erneut – `0.3.2` für Korrekturen, `0.4.0` bei additiven Vertrags- oder Core-Änderungen – und erhält einen eigenen Abschnitt und Tag.

## Modellvalidierung

Änderungen an Modellen oder Konventionen erfordern einen Nachweis gegen eine unabhängige Referenz (QuantLib/ORE, Lehrbuchwert) im Test, einen Eintrag im Methodikabschnitt (`reporting/valuation-report.ts`, `methodologyFor`) und – bei geänderten Bewertungsergebnissen für unveränderte Inputs – eine Anpassung des Golden Masters (ADR-021) mit Begründung im CHANGELOG („Geändert“). Der Core folgt SemVer (ADR-024).
